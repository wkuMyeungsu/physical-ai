1. 전처리 계획

카메라 프레임을 모델 입력으로 만드는 추론 직전의 5단계입니다. 핵심은 원본 해상도에서 얼굴을 자르는 것, 보정은 효과가 확인될 때만 켜는 것, 입력 정규화를 학습과 똑같이 맞추는 것입니다.

  1. 1
    카메라 설정 고정ON

    전원 주파수(60Hz)에 맞춰 노출을 정하고, 자동 노출·화이트밸런스는 완만하게 하거나 캘리브레이션 뒤 잠급니다. 깜빡임과 밝기 출렁임을 입력 단계에서 없앱니다.

    노출 1/120s의 정수배

  2. 2
    프레임 품질 검사ON

    밝기와 선명도를 재서 불량 프레임은 보정하지 않고 버리고 "판정 보류"로 알립니다. 어두운 화면을 억지로 보정하면 잘못된 결과가 나옵니다.

    휘도 40 미만·220 초과, 선명도 기준값의 30% 미만

  3. 3
    얼굴·상체 위치 확보ON

    축소 프레임(640)에서 위치를 찾고 다음 프레임에 이어 씁니다. 여러 얼굴이 잡히면 착석 영역 안의 가장 큰 얼굴을 고릅니다.

    재검출 1~2초마다 또는 추적 실패 시

  4. 4
    얼굴 영역 크롭ON

    원본 해상도에서 잘라 모델 입력 크기로 줄입니다. 축소본에서 자르면 입술 간격이 뭉개집니다(아래 그림). 롤 정렬은 기본 OFF.

    입력 192~256px, 여유 1.3~1.5배

  5. 5
    밝기 보정 · 입력 정규화보정 OFF정규화 ON

    밝기 보정은 얼굴 영역에만, 같은 녹화로 효과가 확인될 때만 켭니다. 입력 크기·채널 순서·mean/std·리사이즈는 학습과 INT8 보정 설정과 완전히 같아야 합니다.

    CLAHE clip 1.5~3.0, 감마 0.6~0.85 / 1.1~1.3

입력 조건 가정 · 쓰지 않는 처리 · 전처리 검증expand_more

입력 조건 가정: 1280×720@30fps, 수평 화각 70~78° 저왜곡, 모니터 상단 중앙·눈높이 이상, 사용 거리 50~80cm, 얼굴 정면 ±30° 이내, 단일 사용자, 60Hz 조명. 마스크·모자·역광 창문은 지원 범위 밖입니다. 현장이 다르면 해당 단계를 다시 설계합니다.

2. 후처리 계획

모델이 낸 점·마스크를 경고 알림으로 바꾸는 단계입니다. 순간적인 동작은 걸러내고, 나쁜 상태가 기준 시간(입벌림 8초, 거북목 30초) 이상 이어질 때만 LCD에 경고를 띄웁니다.

입벌림 판정 사례

  • 발동 기준
  • 해제 기준
  • 그래프 = 입 벌림 비율(MAR)의 시간 변화
  1. 습관성 입벌림멍하니 벌린 상태가 발동 기준 위에서 8초 이어짐
    경고
  2. 말하기짧은 개폐가 반복됨 → 주기 규칙으로 제외
    정상 유지
  3. 하품크게 벌렸다가 곧 닫힘 → 지속 시간 미달로 제외
    정상 유지
  4. 경고 중 잠깐 덜 벌림발동 기준 아래로 내려가도 해제 기준 위면 경고 유지 (깜빡임 방지)
    경고 유지
  5. 컵·손으로 가림입술 점의 신뢰도가 낮음 → 판정 보류, 타이머 정지
    pause판정 보류
  1. A
    사용자 유지

    전처리에서 고른 사용자를 프레임 간 이어서 추적합니다. 지나가는 사람은 무시하고, 수 초 이상 못 찾으면 판정 타이머를 리셋합니다.

    리셋 시간은 실측으로 정함

  2. B
    좌표 정리순서 고정

    불확실한 점 제외 → 왜곡 좌표 보정(광각일 때만) → 튀는 값 제거 → 빠진 값 처리 → 떨림 완화(One Euro). 튄 값이 스무딩에 섞이면 찾을 수 없어서 이 순서입니다.

    결측 0.2초까지 마지막 값 유지

  3. C
    수치 · 개인 기준 비교

    거북목은 얼굴·상체 영역의 겹침·너비 비율·간격(3페이지), 입벌림은 입술 내측 간격 / 입 너비(MAR). 둘 다 약 10초 캘리브레이션으로 만든 개인 기준과 비교합니다.

    거북목은 z-score 결합

  4. D
    판정

    위 사례의 규칙입니다: 두 기준선(발동·해제), 지속 시간, 말하기·하품 제외, 가림·정면 이탈·화질 불량 시 보류.

    입벌림 8초, 거북목 30초~3분

  5. E
    알림 조절

    경고 후 쿨다운·스누즈·일일 상한을 두고, 자세를 고치면 즉시 해제합니다. 기준 자세는 자동 갱신하지 않고, 조명 변화·카메라 이동 때만 재캘리브레이션을 제안합니다.

    수치는 사용자 테스트로 결정

3. YOLO 적용 계획

거북목 판정에 쓸 얼굴·상체 영역을 YOLO-seg로 직접 파인튜닝합니다. 아직 학습 전이라 수치는 목표 또는 시작값입니다.

크기는?
nano · 입력 640n으로 시작해 정체될 때만 s. 올려도 안 오르면 문제는 데이터
학습 모델은?
YOLO26n-segCOCO 사전학습, face·upper_body 2클래스. 보드 변환이 안 되면 YOLO11n-seg
학습 방식은?
전이학습 + 백본 고정freeze=10, AdamW lr 0.001, Colab에서 E0~E5 비교
검증은?
V1 → V5영역·CVA 상관 → INT8 변환 → 보드 지연 → 이벤트 정확도

실험 E0~E5

같은 데이터·시드에서 한 번에 하나만 바꿔 val 마스크 mAP50-95로 비교합니다.

  • E0 점검학습 전 val 1회, 소량으로 설정과 자동 배치값 확인
  • E1 기준nano-seg, freeze=10 (이후 실험의 비교 기준)
  • E2 고정 범위freeze=10 vs 전체 학습
  • E3 크기n vs s, E1이 정체될 때만
  • E4 증강mosaic 0.5 vs 0 (제품 화면은 한 사람이 크게 찍힘)
  • E5 입력 크기640 vs 더 작게, 보드 지연(V3)과 함께

검증 V1~V5

앞 단계가 싸고 빠르므로 통과해야 다음으로 갑니다.

  • V1 영역·신호마스크 mAP, 클래스별 AP. 정면 신호와 측면 CVA의 사람별 순위 상관
  • V2 변환 손실ONNX → RKNN INT8, FP32 대비 mAP·IoU 하락 비교
  • V3 보드 성능해상도별 지연 실측, ≤100ms·3~5fps
  • V4 제품 정확도음료·대화·가림 포함 영상에서 이벤트 단위 ≥95%, 오탐 ≤3%
  • V5 판정 보류가림·화질 불량에서 보류했는지, 너무 잦지 않은지
크기 근거 · 데이터와 라벨링 · 학습 설정expand_more

크기 근거: 720p를 640으로 줄여도 얼굴 폭은 60cm에서 약 115px, 80cm에서 약 85px, 어깨 폭은 약 230px(화각 70° 가정)이라 대상이 큽니다. 클래스가 2개라 nano로 충분할 가능성이 크고, 보드(RK3566급)에서 3~5fps·≤100ms를 지키면서 NPU를 얼굴 랜드마크와 나눠 써야 합니다. 입력을 320으로 줄이면 마스크 한 칸이 약 0.5cm → 1cm로 커져 턱 경계가 거칠어집니다.

4. 모델 비교

YOLOE · DINO-X · SAM 3 · SigLIP · OCR · MediaPipe가 각각 무엇을 하고, 무엇을 받아 무엇을 내며, 어디서 돌아가는지 비교합니다.

이럴 때 이 모델

  • 글로 대상을 지정해 실시간으로 찾고 싶다YOLOE
  • 처음 보거나 드문 물체까지 찾고 싶다 (외부 서버 사용 가능)DINO-X
  • 정확한 윤곽이 필요하거나 영상 속 대상을 따라가고 싶다SAM 3
  • 위치는 필요 없고 이미지를 분류·검색하고 싶다SigLIP
  • 이미지 속 글자를 읽고 싶다OCR
  • 얼굴의 세밀한 점과 표정을 기기에서 실시간으로 얻고 싶다MediaPipe

4개 후보 중 ONNX Runtime을 고릅니다. 보드의 NPU 가속은 이 4개가 아니라 RKNN이 맡고, ONNX Runtime은 같은 모델을 CPU에서 돌려 기준을 잡고 대비하는 엔진입니다.

MCU를 쓰지 않는 이유expand_more
MCU가 맡는 대표적인 일이 제품에서는
즉시 반응하는 안전 제어모터 · 액추에이터가 없음
여러 센서 값 상시 수집센서는 카메라 하나이고 CSI로 SBC에 직결
배터리로 오래 버티기배터리 없음, 항상 USB 전원
화면 · 버튼2인치 LCD는 SBC의 SPI로 1프레임 약 31~38ms, 버튼 1개는 GPIO로 충분

카메라와 TinyML을 지원하는 ESP32-S3만으로 만드는 구성도 검토했지만, 얼굴 검출 정도는 되어도 상체 분할과 입술 랜드마크를 함께 돌리기엔 연산 · 메모리가 부족해서 제외했습니다. MCU를 넣으면 펌웨어, 보드 간 통신, 전원 경로만 늘어나므로 SBC 단독 구성으로 갑니다. 나중에 배터리형으로 바꾸거나 진동 모터 같은 액추에이터를 달면 그때 ESP32-C3급 MCU를 추가합니다.

알아 둘 약점과 대책expand_more
약점내용대책
1. 실제 속도Zero 3에서 YOLO11n을 RKNNLite로 돌렸을 때 프레임당 700~800ms(2~3fps)였다는 사용자 보고. CPU에서 하는 전처리 · 마스크 후처리가 병목마스크는 얼굴 · 상체 1개씩 낮은 해상도로, 분할 3~5fps · 랜드마크 10~15fps로 주기 분리. 모자라면 입력을 640 → 416/320으로 축소
2. 모델 준비RK3566용으로 변환된 얼굴 랜드마크 모델을 찾지 못함PC(x86)에서 ONNX → RKNN으로 직접 변환 (RKNN 변환은 x86에서만 됨)
3. 자료가 적음라즈베리 파이보다 커뮤니티와 예제가 적음보드를 받으면 NPU(rsetup → Overlays) · 카메라 · USB 가젯부터 확인
참고 대안: Pi Zero 2 W + Raspberry Pi AI Camera (보류)expand_more

AI Camera(Sony IMX500)는 카메라 센서 안에서 추론을 해서 Zero 2 W의 약점(NPU 없음)을 메울 수 있고, 라즈베리 파이라 자료가 많습니다(약 $70). 다만 센서 안 메모리가 약 8MB(펌웨어 · 가중치 · 작업 메모리 공유), INT8, 입력 최대 640×640이라 분할 모델과 얼굴 랜드마크 두 개를 함께 올리기 빡빡하고, Zero 2 W의 RAM 512MB도 컨테이너 3개에 부족합니다. ZERO 3W에서 속도가 끝내 안 나오면 다시 검토합니다.

8. SBC 컨테이너 구조

보드 안의 소프트웨어를 Docker 컨테이너 3개로 나눕니다. 모터나 비상정지가 없는 제품이라, 가장 중요한 기준은 "얼굴 영상이 밖으로 나갈 수 있는가"입니다. 영상이 있는 곳과 네트워크가 있는 곳을 서로 다른 컨테이너에 둡니다.

deployed_code컨테이너
3개vision · coach · web
lan네트워크가 있는 곳
web 하나vision · coach는 네트워크 없음
shield가장 중요한 기준
보안하드웨어 접근 권한
hub컨테이너 간 통신
공유 RAM · Unix 소켓보드 안에서만, 네트워크 없이

① vision카메라 캡처 → 품질 검사 → RKNN 추론(상체 분할, 얼굴 · 입술 랜드마크) → 특징값 전송카메라, NPU없음on-failure + mem_limit
② coach거북목 · 입벌림 판정, 캘리브레이션, SQLite 기록, LCD 캐릭터, 버튼, 영상 보기 허락SPI, GPIO없음always
③ web통계 · 설정 웹 페이지, 실시간 보기 중계없음있음always
  1. 1
    실패(패닉) 영향도

    메모리를 많이 쓰는 건 ①뿐입니다. ①이 OOM으로 죽어도 ②가 LCD에 "대기" 화면을 띄우고 ①은 자동 재시작됩니다. 잠깐 멈춰도 되는 구역을 한 컨테이너에 모아 나머지를 지키는 구조입니다. 멈춤(hang)도 재시작되도록 ①은 5초 동안 프레임을 처리하지 못하면 스스로 종료합니다.

    틀린 경고가 굳지 않게

  2. 2
    하드웨어 접근 권한 · 보안가장 중요

    원본 영상은 ①에만 있고 ①에는 네트워크가 없습니다. 밖과 닿는 곳은 ③ 하나뿐이고, ③은 카메라 · 기록에 직접 손대지 못합니다. 모든 컨테이너에 cap_drop: ALL을 주고, privileged 대신 필요한 장치만 연결합니다.

    ①이 뚫려도 영상이 못 나감

  3. 3
    데이터 라이프사이클 · 역할

    수집 · 추론(①) → 판단 · 출력(②) → 외부 창구(③). 원본 프레임은 ① 안의 RAM에서 수십 ms만 살고, 특징값은 쓰고 버리며, 기록 · 기준값 · 설정의 주인은 ② 하나입니다.

    eMMC에는 기록 · 설정만

  4. 4
    라이브러리 의존성

    ①은 rknnlite · OpenCV(NPU 런타임 버전을 커널 드라이버에 맞춰야 해서 따로), ②는 python:3.11-slim · NumPy · spidev · gpiod(PC에서도 그대로 시험 가능), ③은 FastAPI · uvicorn입니다.

    버전 충돌 없음
